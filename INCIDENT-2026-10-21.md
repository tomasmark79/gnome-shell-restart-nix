# Hardware incident: failed theme startup after repeated resets

Investigation date: 2026-10-21. Times below use Europe/Prague.
The initial diagnosis inspected the active desktop read-only. At the user's
request, the first candidate was subsequently activated without restarting the
active Shell. The user logged in again, reset it, and reported that physical
right-click remained broken. Further reproduction and development use VMs.

## Observations from the previous boot

The user reported that the desktop background's right-click menu stopped
working, followed eventually by an unusable Shell. The previous session's
Shell process recorded successful old-context finalizations at 11:34:18 and
11:46:04. At the third reset, 13:04:15, the old context finalized but new UI
startup failed:

```text
g_object_ref: assertion 'G_IS_OBJECT (object)' failed
TGNOME runtime startup failed Error: Argument file may not be null
loadTheme ... main.js
```

That same process remained alive until system shutdown at approximately
13:05:51. The evidence therefore establishes failed UI reinitialization, not
a recorded native process crash at that point. No corresponding Shell core
dump was found for this late failure.

Earlier logs repeatedly show `Vfunc delegate is still attached` while Dash to
Dock hooks or restores `vfunc_allocate`, including after screen-shield/session
mode transitions. This also occurs at initial startup before any context reset.
The current fresh session exhibits the same initial extension error.

## Reproduced mechanisms

### Same-context vfunc injection rejected by our bridge

The experimental permanent bridge rejected an override whenever a delegate was
already attached. That is too strict: extensions legitimately replace and
restore virtual methods within the same live GJS context.

The fix permits replacement within the owning context while continuing to reject
replacement by another live context. An invalidation notifier clears the bridge
only if the invalidated closure is still its active delegate; an older closure
must not clear a replacement. The native probe now overrides/restores a method
in each of three successive runtimes, checks native dispatch, and verifies old
context release and safe calls during the gap. Direct and Valgrind runs pass.

### Duplicate custom stylesheets leave an invalid file entry

`St.Theme.load_stylesheet()` could add the same stylesheet twice. A later
`unload_stylesheet()` removed one list entry and the file lookup mapping,
leaving another list entry without a corresponding GFile. A subsequent
`get_custom_stylesheets()` / `Main.loadTheme()` encountered a null file.

A separate busless process using the installed candidate reproduces both the
GObject assertion and `Argument file may not be null`, without a desktop or
context reset. The patched St implementation makes an already-active load
idempotent. The same test then passes 20 load/load/unload cycles with no stderr.

Repeated failed extension enables and stylesheet reloads provide a plausible
route to this state in the hardware session. The exact stylesheet list from the
failed process was not captured, so its full historical sequence is inferred,
not independently reconstructed.

## Background menu scope

The journal alone did not explain the gesture failure. The first added test
only opened the menu programmatically and missed it. A subsequent VM test sends
real virtual-hardware pointer motion and a secondary-button press/release
through QEMU, minimizing fixture windows to expose the desktop. Before reset
the menu opens; immediately after the first reset it does not, although the
click reaches a reactive MetaBackgroundActor. This reproduces the user's report.

LayoutManager creates its background group inside Mutter's persistent
`global.window_group`, outside the disposable `uiGroup`. The upstream shutdown
handler preserves window_group and destroys uiGroup; it never destroys the
separate background group because normal process exit makes this unnecessary.
During our reset, each new background group is inserted below its predecessor.
The old reactive background survives with disconnected JS callbacks and receives
clicks above the new live background. Programmatically opening the new menu
therefore passes while an actual click fails.

The reset handler now cancels pending background loading, destroys its background
managers and background group while the old JS context is valid, then performs
the existing UI teardown. The pointer regression requires actual menu opening,
mapping, exactly one background group and a hit on the current background before
reset, after each of five resets, and after lock/unlock. Initial attempts using
a GJS virtual pointer had unsuitable coordinates; the QEMU input test replaces
them rather than treating those attempts as product evidence.

## Reproduce the focused controls

```sh
theme_shell=$(nix build --no-link --print-out-paths .#native-shell)
python3 tests/theme-supervisor.py "$theme_shell"
nix develop .#type-rebind -c python3 tests/type-rebind-supervisor.py \
  tgnome-type-rebind-probe artifacts/incident-native-control.json
nix build --no-link .#full-context-desktop-vm
```

The desktop-integration VM adds the locked nixpkgs Dash to Dock package
(version 105). The hardware session used version 110, so that exact extension
version remains a separate compatibility check. Historical minimal-fixture
passes did not establish arbitrary extension compatibility or long-session
reliability. A new native build requires activation and a new login before the
personal session can acquire these fixes.

## Verification and deployment

The final desktop-integration VM passed five complete runtime replacements,
including two physical Alt+F2/r requests. Hardware pointer right-click opens the
menu before reset, after all five resets, and after real lock/PAM unlock. Every
check finds exactly one background group and hits the current background actor.
Original Wayland/XWayland sockets and subsequent keyboard input, custom Super+T,
enabled Dash to Dock, wrong-password rejection, the 65-second observation and
empty retired callback ledgers also pass. An independent VM run without the
additional post-unlock pointer assertion passed all five pointer/reset cycles.

The updated headless suite passed five cycles; the combined evidence verifier
and all 12 CLI safety checks passed. See the redacted
[incident evidence](evidence/2026-10-21-background-pointer.json).

The corrected system configuration was activated at the user's request, keeping
the active Shell process alive. A new login is required to load the corrected
binary. Physical desktop confirmation with the user's exact extensions remains
pending; VM success is not a claim of long-session hardware reliability.
